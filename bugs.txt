A. Errors in the document itself
§9 "Porting gotchas" contradicts §2/§7 about skyBand. The document says in §9 that _drawEntityClip uses H + skyBand = 169 "instead of H + J = 113". But §2 (i.js:518) and the code comment define this.skyBand = 169 - this.H, that is, H + skyBand = 169 — exactly what Java does when J (int, i.java:505) is never assigned (it remains 0): H + J = 76 + 0 = 76… and, in addition, c(Graphics) in i.java:4045-4051 splits the sky into H..H+J and H+J..169, which only tiles correctly if J = 169 − H = 93. The value "113" does not appear anywhere; the document's reasoning is internally inconsistent. Note: the document also states I=93 and J=I*40/100=37 (§7), values that come from the <clinit> dumped as commented bytecode (i.java:7017-7023) and are correct in that context, but conflict with the interpretation of J used in §9.
§3.2 describes the pass dispatch incorrectly. It says "paramInt 1/0: _drawEntityClip" and "paramInt 2: _drawEntityMask", omitting that cases 1 and 0 are literally identical in both JS and Java (i.java:4020-4026) — this is faithful, but the document suggests a nonexistent difference between passes.
§7 states that "tuftCount remains 0, faithfully" because i7 === 66 never occurs. This is correct for the current calls, but the document does not mention that the actual Java gate is if (h.a != null && paramBoolean && paramInt14 <= 0), with scatter counter a compared to the length of u; in JS, the equivalent this.tuftEnabled is initialized to true (i.js:441), while the method's own comment (i.js:7060-7070) says it represents the h.a != null test. If the __WM_DEBUG_TUFTS toggle is enabled, scatter runs in every entity band and contaminates this.a (the Random shared with gameplay) — an undocumented side effect.

B. Actual sprite-rendering bugs found in the code
_playEntityAnim throws ReferenceError (the animation sprite is never drawn). i.js:3749: a(paramInt1, paramInt2, b, paramGraphics); calls the bare identifier a, which is declared at module scope (i.js:15) as let a but is uninitialized → TDZ/undefined. It should be i._drawEntityAnim.call(this, ...) or the equivalent helper. In Java (i.java:4380-4400), that call invokes a(int,int,int,Graphics), another method. Since _drawEntityMask wraps the call in a silent try/catch(_e){}, the symptom is that "the special animation (b=18/19/20/21) simply does not appear". The same broken pattern occurs in renderRegion (i.js:3752-3786): it uses bare a(d, e, 0, 7), h, d, e — it never works (it always falls into the catch).
Arguments swapped in _drawEntityOverlay / _getTerrainColor — entity shadow/overlay is drawn with the wrong color/type. Java i.java:4349 (a(int i1, int i2, int i3, byte b1, byte b2, Graphics g, boolean)) calls a(b1, b2, 13, 57344) — tile coordinates first. In JS, i.js:3702-3703 calls i._getTerrainColor.call(this, paramInt4, paramInt5, 13, 57344), where paramInt4/paramInt5 in the JS signature are (w, kind), not (tileX, tileY). Compare with _drawEntityObject (i.js:3674), which correctly passes (paramInt5, paramInt6, ...) according to its parameter order. Result: sprites 266/267/268/357/358/359 (house/object overlays) are read from incorrect tiles or suppressed (case 3: return).
_getTerrainColor reads the wrong variable for day/night state. i.js:4562-4579: the function compares if (i === 5) ... using the module identifier i (the exported class!), not this.i (the game clock). In Java (i.java:5135-5153), this is the static i = hour. Since i is the class function, all branches yield bool = false, so hColorThresholds[...][false] always selects column 0: terrain/entity gradient colors are systematically those for "early night", regardless of the time. This is a direct visual bug.
Floating-point division in _drawTileGradient disables horizon detail. i.js:6822: if (paramInt2 === this.H * 70 / 100) — in JS, 76*70/100 = 53.2, which can never equal an integer; it is missing | 0, which was applied in renderTileColumn16 (i.js:7013, noted in its comment). Also, the inner block (i.js:6823-6846) reimplements Java's randomness (a(95,105,Random) and a(paramInt6,paramInt10,Random), i.java:7384-7399) with deterministic formulas 95 + b*3 and a uniform distribution across the width — a confirmed visual divergence. And i.js:6851 uses this.h.a !== null where this.h is a number (heading) → TypeError caught by the silent try/catch(_e){}: lateral gradient scatter never runs (Java does this because h there is an instance of class h with field a).
_drawEntityClip: suspicious clipping arithmetic is replicated, plus incorrectly typed buffers. i.js:3642: paramInt4 = paramInt2 + m - this.H + this.skyBand; this replicates the apparent precedence bug in i.java:4266 (paramInt2 + m - H + J); with skyBand=93, it adds 93 instead of subtracting the band, producing absurd pass heights if an entity crosses the boundary (it does not currently, coincidentally because the boundary at 169 is the lower edge). Additionally, resetGameState (i.js:427-431) assigns this.d = Array(130).fill(false) and this.e = Array(130).fill(false) — the player fields! — as boolean arrays, although i.js:505-506 later resets them to 0. Any read of this.d/this.e before the map is loaded produces [false]+offset = 0+offset (string concatenation→NaN in b2/b3 in _renderEntitiesInner, i.js:3358), and catch(_e){continue;} hides the failure: entire entity columns disappear from rendering.
renderCell20 is indexed with an out-of-range heading. i.js:6908: hDayBounds[paramInt16], where paramInt16 comes from paramInt5 (= m in _drawEntityClip, ranges 1..8 and 1..3) — this matches Java. However, _drawTerrainColumnInner (i.js:3841) uses !this.h || this.h === 4 ... and then hDayBounds[paramInt7], where paramInt7=band (0 or 1), mixing this with Java's boolean semantics for h (see point 10): the day/night selector in both places treats this.h as though it were Java's boolean h (alternate render mode), while in this port this.h is heading 0..8. With headings 4, 2, 6, 0 it forces "day"; with 1,3,5,7,8 it forces "night": water/entity bands use the opposite season's bounds depending on the player's orientation.
Conflicting identity of h is documented but unresolved. Java has public static boolean h (i.java:439, toggled in v()/key 13), and heading is represented by another letter merged by the decompiler. The port chose this.h = numeric heading (i.js:498) but retained inherited boolean conditions (i.js:3841, 6908, 1346: this.h = !this.h — it toggles the heading to true/false!). After pressing key 13, hDayBounds[this.h] is indexed with true/false → undefined[b*2] → swallowed exception → black entity screen after that input. This is probably the most visible sprite bug.

C. Verified minor risks
randomInt (i.js:606) uses Math.random (documented in §6), but is also an instance method while Java uses a static method; the tuft block in renderTileColumn16 no longer calls it, OK.
drawSprite in resources/c.js silently skips unknown sprites (_missRow), consistent with Java; not a bug.
The star loop (i.js:3494-3502) is protected by an empty try{}catch(_e){}: if byteArrB/C/intArrC are not populated, the night sky has no stars and there is no log.
Summary: the document describes the architecture well but contains a contradiction about skyBand/J (§A.1) and omits that several sprite-rendering paths are silently broken by empty try/catch blocks: _playEntityAnim/renderRegion (ReferenceError from bare a), _drawEntityOverlay (swapped parameters), _getTerrainColor (compares class i instead of this.i), _drawTileGradient (missing |0, nonexistent this.h.a), and the fatal overloading of this.h (heading vs. boolean, toggled by key 13).
